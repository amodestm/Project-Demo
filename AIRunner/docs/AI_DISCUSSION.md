# 多账号 AI 讨论组（AI Discussion）

用多个 ChatGPT 账号组成一个**可配置的讨论组**：每个账号扮演一个立场互斥的角色，围绕同一议题**独立论述 → 交叉质询 → 收敛出决策**。全程由 AIRunner 通过 macOS 辅助功能（AX）API 在你的 Chrome 窗口之间切换完成，不需要人工复制粘贴。

---

## 1. 为什么需要"角色互斥"

所有账号背后都是同一个 ChatGPT。如果角色设定不互斥，讨论必然退化成互相附和——这是本功能最大的隐性风险（回声室）。

因此内置的角色模板**刻意只给一个维度、并明确禁止越界**，用"强制片面"换取观点差异：

| 角色 | 只负责 | 明确禁止 |
|---|---|---|
| 批判者 | 找逻辑漏洞、未经验证的假设、失败场景 | 不许提建设性意见，不许肯定任何人 |
| 成本专家 | 估算时间 / 金钱 / 人力开销 | 不许谈体验与技术优雅性 |
| 乐观派 | 找机会与上行空间 | 不许讨论风险 |
| 用户代言人 | 使用体验、学习成本、真实需求 | 不许谈技术实现难度与内部成本 |
| 风险官 | 最坏情况、不可逆后果 | — |
| 执行者 | 可执行性、前置依赖、第一个动作 | 不许评价方案好坏 |

自定义角色时请沿用这个原则：**写清楚"这个角色专门负责挑什么毛病"，并明确它不许越界谈什么。**

## 2. 配置模型

```
DiscussionGroup                 一次讨论的配置（可复用、可持久化）
├─ name / topic                 组名 + 议题（要决策的问题）
├─ participants: [Participant]
│   ├─ displayName              显示名，如「批判者」
│   ├─ rolePrompt               角色设定（制造认知差异的唯一手段）
│   ├─ avatarSymbol / accentHex 头像符号与配色（多成员一眼可分）
│   ├─ profileDirectory         绑定的 Chrome Profile，如 "Profile 3"
│   ├─ emailHint                账号校验标识，用于确认"这个窗口确实是这个账号"
│   └─ enabled
├─ rounds: [RoundConfig]        议程（轮次顺序可配）
├─ consensus: ConsensusRule     收敛规则
└─ moderatorParticipantID       主席成员（留空则取第一个启用成员）
```

一条讨论记录如下：

```
DiscussionRun        运行状态（落盘，可崩溃恢复）
├─ state: idle → running → waitingForResponse → converged / failed / cancelled
├─ currentRound / currentParticipantID
├─ finalDecision     最终决策
└─ utterances: [Utterance]
     ├─ promptSent / responseText      发出与收到的完整原文
     ├─ accountEmailUsed               实际使用的账号（审计：防止发错人）
     └─ status: pending / sent / received / failed
```

## 3. 议程：轮次与可见性

每一轮有三个可配维度：**性质**、**本轮指令**、**可见性**。

| 轮次性质 | 语义 | 默认可见性 |
|---|---|---|
| 独立论述 | 各成员看不到任何人的发言，避免被带节奏 | 不看他人 |
| 交叉质询 | 能看到他人发言并反驳 | 看他人 |
| 收敛决策 | 汇总所有发言，产出最终结果 | 看他人 / 看全部 |

可见性三档：**不看他人** / **看他人**（不含自己上一轮）/ **看全部**。

- 发言人顺序可显式指定；留空则按配置顺序使用全部启用成员。
- 收敛轮默认只让主席发言；但选择**多数投票 / 一致同意**时，全体成员都发言（投票要求相互独立，见下）。
- 默认议程即「独立论述 → 交叉质询 → 主席收敛」三步，开箱可用。

---

## 4. 收敛规则

| 规则 | 行为 |
|---|---|
| 主席汇总 | 主席读完所有发言后给出最终决策与理由 |
| 多数投票 | 各成员独立投票取多数；平票时由主席裁决 |
| 一致同意 | 必须全部赞成，否则判定不通过 |
| 主席独裁 | 主席直接拍板，不要求汇总理由 |

投票规则下，prompt 会强制成员在**最后一行**输出 `VOTE: YES` 或 `VOTE: NO`（全角冒号也接受）。AIRunner 自下而上扫描解析；任一成员格式不合规会明确报错指出是谁，而不是静默算错票。

> **投票隔离**：同一收敛轮里，后投票的成员看不到前人的票——只把**本轮之前**的发言喂给它，避免从众。

## 5. 使用流程

### 前置条件

- 在 Chrome 中建立至少两个 Profile，并在每个 Profile 分别登录一个 ChatGPT 账号。
- 给 AIRunner 授予**辅助功能**权限（系统设置 → 隐私与安全性 → 辅助功能）。

### 操作步骤

1. 主界面打开**讨论组**面板。
2. **新建**讨论组 → 自动生成 3 个互斥角色 + 默认议程。
3. 点**配置**：
   - 填写**议题**；
   - 检查/编辑每个成员的**角色设定**（这是讨论质量的决定性输入）；
   - 点**一键分配**，从本地检测到的 Chrome Profile 中自动为未绑定成员分配不同账号；点**随机换一批**可打乱 Profile 池重新分配；
   - 按需增删**轮次**、调整**可见性**与**收敛规则**、指定**主席**。
4. 顶部选择**会话模式**（见下节）。
5. 点**开始讨论**。界面按轮次实时显示发言气泡、正在思考的成员，结束后给出决策卡片。

底部按钮会随状态切换：进行中为**停止**；失败时为**重试本次讨论**（从断点续跑）或**重新开始**（清空重来）；收敛后为**再讨论一次**（新开一场，旧运行保留供审计）。

### 执行模式

| 模式 | 用途 |
|---|---|
| **真实 Chrome** | 驱动各成员绑定的已登录 Profile 发起真实讨论。要求启用成员 ≥ 2 且全部绑定了 Profile 与账号标识，否则开始按钮会被禁用并提示还差哪些成员。 |
| **脚本演示** | 用预设脚本回复跑通完整流程（论述→质询→收敛），不调用任何网页。用于离线验证配置与议程是否正确。 |

模式不会被静默切换：真实模式下若成员未绑定 Profile，**直接报错停止**，不会偷偷降级成演示模式冒充真实讨论。

## 6. 两条铁律

### 铁律 1：身份校验 fail closed

每次发言前都校验目标窗口的登录账号是否与该成员绑定的一致。不匹配时**立即停止整场讨论**，报错明确指出"期望哪个账号、实际是哪个账号"。

发错人 = 整场讨论作废，因此这里没有"继续试试"的余地。`emailHint` 就是为此存在的——Chrome Profile 名与真实登录邮箱不一致时，请把真实邮箱填进去。

### 铁律 2：收到即落盘

每条发言在收到回复的瞬间就原子写入数据库。崩溃、强杀、断网后重新打开，会从**最后一条完成的发言**继续，绝不重复已经说过的内容，也不会重跑已推进的轮次。

因此本项目**不读取、不导出、不注入浏览器 Cookie / session token**；切换的是你合法持有的账号，复用 Profile 中已有的网页登录。遇到验证码 / 人机验证 / 2FA 会停止并提示你处理，不尝试绕过。

## 7. 数据与持久化

讨论配置、运行状态与全部发言都存入 AIRunner 的 SQLite 数据库（`~/Library/Application Support/AIRunner/airunner.sqlite`）：

| 表 | 内容 |
|---|---|
| `discussion_groups` | 讨论组配置（成员、轮次、收敛规则） |
| `discussion_runs` | 每次运行的运行时状态与最终决策 |
| `discussion_utterances` | 每条发言的完整留痕（prompt 原文、回复原文、实际使用账号） |

每条发言都标注了**实际使用的账号**，所以任何一场讨论都可事后审计：谁说了什么、用的是哪个账号。

## 8. 架构：串行 · 多窗口常驻

讨论组的执行方式是**一次只驱动一个会话**：把目标成员对应的 Chrome 窗口置前 → 写入 prompt → 提交 → 读回结果 → 切下一位。

之所以不并行，是因为在这条链路上并行需要依赖"对后台窗口写入 AX 值"——部分应用会丢弃失焦窗口的写入或重置焦点，稳定性代价远高于收益。串行路径走的是**前台操作**，与 AIRunner 既有的账号切换代码路径完全一致，可靠性已经被验证。

功能上并没有因此变慢：单个窗口只需要**切换**，不需要反复退出登录、重新走 OAuth。

层级上，讨论组走的是 **Chrome 网页版 ChatGPT** 这条线（与 `WebExecutionCoordinator` / 账号切换同源），复用同一套持久化与编排设施；Codex 桌面端那条 OAuth 驱动链路不受影响，两条线互不污染。

```
DiscussionOrchestrator (actor 语义，主线程)
  ├─ 逐轮推进议程  → 逐成员发言
  ├─ RoutingDiscussionSessionProvider   真实 Chrome / 脚本演示 路由
  │     └─ ChromeDiscussionSession      锁定窗口 · 身份校验 · 提交 · 读回
  └─ DiscussionRepository  → SQLite（发言收到即原子落盘）
```

## 9. 边界与已知限制

- **同质模型**：所有成员背后都是同一个 ChatGPT，讨论质量完全取决于角色 prompt 的差异化程度。角色互斥性不够时，输出会明显趋同。
- **窗口依赖**：真实模式需要对应的 Chrome 窗口处于可用状态；窗口被关闭或 Profile 登录态失效时会在身份校验环节 fail closed 停止。
- **账号数上限**：成员数受可用 Chrome Profile 数限制，一个 Profile 只能绑定一个成员。
- **不做的事**：不绕过验证码 / 人机验证，不使用 API 通道做多模型讨论。
