# AI 议事会（AIDiscussion）

macOS 原生应用：把**多个已登录的 ChatGPT 账号**组成一个可配置的讨论组，各自扮演**立场互斥**的角色，围绕同一议题**独立论述 → 交叉质询 → 收敛出决策**。

全程由应用通过 macOS 辅助功能（AX）API 在你的 Chrome 窗口之间切换完成——不需要人工复制粘贴，也不需要 Selenium / Playwright。

---

## 核心功能

- **多账号讨论组**：每个成员绑定一个已登录的 Chrome Profile，一个讨论组就是一支"团队"。
- **真正的静默后台运行**：不抢占前台输入焦点，也不安装全局键盘 / 鼠标钩子。所有操作都定向发往目标窗口，因此**你可以边跑讨论边正常使用电脑**。
- **窗口可移出屏幕视野**：一键把参与讨论的 Chrome 窗口移出可视区域，讨论 100% 不弹窗打扰；需要看实时页面时再一键移回。
- **开跑前集中预热**：开始讨论时先一次性把全部成员的窗口打开、就绪并静默后置，随后整场讨论都在后台完成，不会每换一位成员就弹一次窗。配置页也可手动点「提前打开全部窗口」预先把窗口备好。
- **复用已开的窗口**：如果某个账号已经有打开着的 ChatGPT 窗口，直接复用，不重复开窗。
- **未登录一键直达**：检测到某位成员未登录时会明确指出是谁（含 Profile 名），并给出「一键跳转登录」按钮，直接以该 Profile 打开登录页。
- **自动切到高推理强度**：自动检测网页端的思考强度控件并切到「高」，让每个成员都按深度思考模式作答。
- **联网搜索过渡态识别**：会识别「正在搜索 N 个网站 / Searching the web / 已搜索」等中间状态，不会把搜索占位符当成最终回答读回来。
- **「继续讨论」断点续跑**：中断、报错或手动停止后保留已有发言，点一下从**下一个成员**接着推进，不重复已说过的内容。
- **身份校验 fail closed**：每次发言前核对目标窗口的登录账号，不匹配就立即停止整场讨论——发错人等于整场讨论作废。
- **发言收到即落盘**：每条发言在收到回复的瞬间原子写入数据库，崩溃或强杀后可恢复。
- **零外部依赖**：纯 SwiftPM 工程，Xcode 直接打开即可构建，无需 resolve 任何 package。
- **可被 Codex 等 MCP 客户端调用**：内置 MCP 服务端，外部 AI 能自带角色临时组一场讨论、
  拿到结论后接着干自己的活，或复用界面里配好的讨论组。详见 [让 Codex 调用（MCP）](#让-codex-调用mcp)。

## 为什么强调"角色互斥"

所有账号背后都是**同一个** ChatGPT。如果角色设定不互斥，讨论必然退化成互相附和——这是这类应用最大的隐性风险（回声室）。

因此内置的角色模板**刻意只给一个维度，并明确禁止越界**，用"强制片面"换取观点差异：

| 角色 | 只负责 | 明确禁止 |
|---|---|---|
| 批判者 | 找逻辑漏洞、未经验证的假设、失败场景 | 不许提建设性意见，不许肯定任何人 |
| 成本专家 | 估算时间 / 金钱 / 人力开销 | 不许谈体验与技术优雅性 |
| 乐观派 | 找机会与上行空间 | 不许讨论风险 |
| 用户代言人 | 使用体验、学习成本、真实需求 | 不许谈技术实现难度与内部成本 |
| 风险官 | 最坏情况、不可逆后果 | — |
| 执行者 | 可执行性、前置依赖、第一个动作 | 不许评价方案好坏 |

自定义角色时请沿用这个原则：**写清楚"这个角色专门负责挑什么毛病"，并明确它不许越界谈什么。**

## 配置模型

```
DiscussionGroup                 一次讨论的配置（可复用、可持久化）
├─ name / topic                 组名 + 议题（要决策的问题）
├─ participants: [Participant]
│   ├─ displayName              显示名，如「批判者」
│   ├─ rolePrompt               角色设定（制造认知差异的唯一手段）
│   ├─ avatarSymbol / accentHex 头像符号与配色（多成员一眼可分）
│   ├─ profileDirectory         绑定的 Chrome Profile，如 "Profile 3"
│   ├─ emailHint                账号校验标识，用于确认"这个窗口确实是这个账号"
│   └─ enabled
├─ rounds: [RoundConfig]        议程（轮次顺序可配）
├─ consensus: ConsensusRule     收敛规则
└─ moderatorParticipantID       主席成员（留空则取第一个启用成员）
```

### 议程：轮次与可见性

每一轮有三个可配维度：**性质**、**本轮指令**、**可见性**。

| 轮次性质 | 语义 | 默认可见性 |
|---|---|---|
| 独立论述 | 各成员看不到任何人的发言，避免被带节奏 | 不看他人 |
| 交叉质询 | 能看到他人发言并反驳 | 看他人 |
| 收敛决策 | 汇总所有发言，产出最终结果 | 看他人 / 看全部 |

可见性三档：**不看他人** / **看他人**（不含自己上一轮）/ **看全部**。发言人顺序可显式指定；留空则按配置顺序使用全部启用成员。默认议程即「独立论述 → 交叉质询 → 主席收敛」三步。

### 收敛规则

| 规则 | 行为 |
|---|---|
| 主席汇总 | 主席读完所有发言后给出最终决策与理由 |
| 多数投票 | 各成员独立投票取多数；平票时由主席裁决 |
| 一致同意 | 必须全部赞成，否则判定不通过 |
| 主席独裁 | 主席直接拍板，不要求汇总理由 |

投票规则下会要求成员在**最后一行**输出 `VOTE: YES` 或 `VOTE: NO`（全角冒号也接受）。任一成员格式不合规会明确报错指出是谁，而不是静默算错票。同一收敛轮里，**后投票的成员看不到前人的票**——只把本轮之前的发言喂给它，避免从众。

## 快速开始

```bash
swift build
swift test

# 组装可双击的 .app（含 ad-hoc 签名）并安装到 /Applications
bash Scripts/make_discussion_app.sh release
open /Applications/AIDiscussion.app
```

也可以直接双击仓库根目录的 `启动 AI议事会.command`：已安装则直接打开，未安装则自动编译打包后再打开。

用 Xcode 打开：`open Package.swift`，选 `AIDiscussion` scheme 运行。

### 首次使用

1. 在 Chrome 中建立至少两个 Profile，并在每个 Profile 分别登录一个 ChatGPT 账号。
2. 打开应用 → 新建讨论组。
3. 点**配置**：填写议题；检查 / 编辑每个成员的**角色设定**；点**一键分配**从本地检测到的 Chrome Profile 中自动分配不同账号（**随机换一批**可打乱 Profile 池重新分配）。
4. 回主界面授予应用**辅助功能**权限（系统设置 → 隐私与安全性 → 辅助功能），然后点**开始讨论**。

运行中界面按轮次实时显示发言气泡与正在思考的成员，结束后给出决策卡片。中断后底部按钮会变成**继续讨论**，从下一个成员续跑；若某位成员未登录，界面会直接给出**一键跳转登录**。

> 建议先在配置页点一次**提前打开全部窗口**，把各成员的窗口预热就绪——这样正式讨论就能全程后台静默跑完，不会中途弹窗。

## 数据位置

| 内容 | 位置 |
|---|---|
| 讨论组 / 运行状态 / 发言 | `~/Library/Application Support/AIDiscussion/aidiscussion.sqlite` |
| Profile 别名（账号标识） | 同一数据库 |

数据库包含三张表：`discussion_groups`（配置）、`discussion_runs`（运行时状态与最终决策）、`discussion_utterances`（每条发言的 prompt 原文、回复原文、**实际使用的账号**）。每条发言都标注实际账号，因此任何一场讨论都可事后审计。

## 让 Codex 调用（MCP）

讨论组可以作为一个 **MCP 服务端**被外部客户端调用。配置之后，Codex（或任何 MCP 客户端）能直接：

- 自带角色设定、临时组一个讨论组，跑完拿到结论，然后**接着干它自己的活**；
- 也可以复用你在这个 app 里已经配好的讨论组，只换一个议题；
- 长讨论可以异步起、轮询查进度、最后取结论。

### 它是怎么接起来的

```
Codex / 其它 MCP 客户端
   │  stdio（换行分隔 JSON-RPC）
   ▼
AIDiscussionMCP 可执行文件          ← 只是代理，不碰浏览器
   │  Unix domain socket（0600 + 随机 token）
   ▼
AIDiscussion.app                    ← 持有辅助功能权限，真正驱动 Chrome
```

三个关键点：

- **权限在 app 上，不在 MCP 上**。驱动网页 UI 依赖辅助功能权限，而那个授权给的是 app。
  所以 MCP 只是转发，你**不需要**再给命令行程序单独授权。
- **app 没跑会自动拉起**。MCP 会先试 `open -b com.aidiscussion.app`，再回退到
  `/Applications/AIDiscussion.app` 和仓库里的 `dist/AIDiscussion.app`，然后等桥接就绪。
- **讨论跑在 app 里，不在 MCP 进程里**。所以 Codex 那边中断了，讨论照样跑完并落盘，
  事后用 `discussion_result` 取结论即可（界面侧边栏也会实时显示进度）。

### 配置

```bash
# 1. 构建 MCP 服务端
swift build -c release --disable-sandbox

# 2. 打印要写进 ~/.codex/config.toml 的配置（默认只打印，不改文件）
bash Scripts/install_mcp_config.sh

# 3. 确认无误后再落盘（幂等：已有同名段落则不动）
bash Scripts/install_mcp_config.sh --apply
```

写入的内容形如：

```toml
[mcp_servers.aidiscussion]
command = "/绝对路径/.build/release/AIDiscussionMCP"
args = []
startup_timeout_sec = 60
```

然后**重启 Codex**。注意 `command` 指向的是构建产物；如果执行过 `swift package clean`，
需要重新构建（或把该二进制拷到一个不会被清理的固定路径，再改这行）。

也可以手工把上面这段贴进 `~/.codex/config.toml` —— 脚本默认只打印，就是为了避免
在你正在用的配置里自动动刀。

### 工具

| 工具 | 作用 | 关键参数 |
|---|---|---|
| `discussion_run` | 跑完一场讨论并直接给结论（**阻塞**） | `topic`、`participants`／`group`、`rounds`、`consensus`、`timeoutSeconds` |
| `discussion_start` | 异步起一场讨论，立刻返回 `jobId` | 同上（无 `timeoutSeconds`） |
| `discussion_status` | 查进度；**不带 `jobId` 时返回桥接状态**（app 是否在跑、权限、可用 Profile、在跑的任务） | `jobId`（可选） |
| `discussion_result` | 取结论 + 每位成员发言全文 + 账号审计 | `jobId`、`maxCharsPerUtterance` |
| `discussion_cancel` | 取消任务（已完成的发言保留） | `jobId` |
| `discussion_roles` | 列出 6 个内置角色模板 | — |
| `discussion_profiles` | 列出可绑定的 Chrome Profile 与建议账号标识 | — |
| `discussion_groups` | 列出你在界面里配好的讨论组 | — |

成员（`participants`）每项至少要给 `name`，角色用 `role`（自定义）或 `preset`（内置模板名）；
`profile` 不给就自动分配一个未占用的；`account` 不给就取该 Profile 的显示名。

### 怎么用才不浪费

- **阻塞还是异步**：预计 10 分钟以内用 `discussion_run`；更长的用
  `discussion_start` + `discussion_status` 轮询，避开客户端工具超时。
  `discussion_run` 超时**不等于失败**，任务仍在跑 —— 按返回的 `jobId` 改用轮询即可。
- **角色必须互斥**。所有账号背后是同一个模型，若每个角色都写"客观全面地分析"，
  讨论必然退化成互相附和。写清「专门负责挑什么毛病」+「不许越界谈什么」。
  不确定就用 `discussion_roles` 的模板。
- **别用它查事实**。决策、取舍、风险评估才值得开会；查资料直接查。

### 权限与故障排查

| 现象 | 原因与处理 |
|---|---|
| `discussion_status` 说"辅助功能权限：未授予" | 到「系统设置 → 隐私与安全性 → 辅助功能」勾选 AIDiscussion |
| 工具报"未在运行，且无法自动启动" | 手动打开 AIDiscussion.app 后重试；app 必须至少启动过一次 |
| 工具报 `login_required` | 某位成员没登录：在 app 里点「一键跳转登录」，或按返回的 `loginURL` 登录该 Profile |
| 工具报 `invalid_request` 且提到 Profile | 先调 `discussion_profiles`，用返回的 `directory` 值 |
| 想确认到底连没连上 | 调 `discussion_status`（不带参数），它会报 app 版本、协议版本与权限状态 |

### 安全边界

- 桥接只监听**本机文件系统里的 Unix socket**，不占端口、不经网络。
- `bridge.sock` 与 `bridge.token` 都是 `0600`，只有当前用户可读写；
  请求还要带 64 位随机 token（app 每次启动重新生成），其它本机程序无法顺手驱动你的讨论。
- MCP 侧不读取任何凭据，也不联网；它只把 JSON 转给 app。

```

  └─ DiscussionHubView                 讨论组列表 + 运行界面 + MCP 桥接面板
       ├─ DiscussionConfigView          成员 / 议程 / 收敛规则配置
       └─ DiscussionOrchestrator        按议程串行推进，逐成员发言
            ├─ DiscussionSessionProviding  会话提供方抽象
            │    └─ ChromeDiscussionSession 锁窗 · 身份校验 · 写入 · 提交 · 读回
            │         └─ ChromeProfileScanner  读取 Chrome profile / 按 profile 开窗
            └─ DiscussionRepository     → SQLite（发言收到即原子落盘）
  └─ DiscussionBridgeServer            Unix socket 桥接（外部调用入口）
       └─ DiscussionBridgeHub          任务注册表 · op 分发 · 进度快照

AIDiscussionMCP（可执行）              MCP stdio 服务端 → 连上面的 socket
AIDiscussionMCPKit（库）               MCP 协议 · 工具面 · 桥接客户端
AIDiscussionBridge（库）               与 app 共用的线协议
AIDiscussionCore（库）                 零 UI 依赖，可单独引用
```

### 为什么是串行

讨论组**一次只驱动一个会话**：把目标成员对应的 Chrome 窗口置前（或移出屏幕视野）→ 写入 prompt → 提交 → 读回结果 → 切下一位。

并行需要依赖"对后台窗口写入 AX 值"，而部分应用会丢弃失焦窗口的写入或重置焦点，稳定性代价远高于收益。串行路径与"账号切换"复用同一条已验证的代码路径，可靠得多——而且切换窗口只需不到一秒，并没有因此变慢。

## 隐私与安全

- **不读取、不导出、不注入浏览器 Cookie / session token**；账号切换复用 Profile 中已有的网页登录。
- **不安装全局键盘 / 鼠标钩子**（无 `cghidEventTap` 一类的全局事件监听），所有输入都定向发往目标窗口。
- 只读 Chrome `Local State` 中**用户自己给 profile 起的名字**，不读 `gaia_name` 一类的账号字段。
- 遇到验证码 / 人机验证 / 2FA 会停止并提示你处理，不尝试绕过。
- 数据库只保存讨论内容与实际使用的账号标识，用于事后审计。

## 能做什么（预想用法）

下面这些是这套东西**已经具备实现条件**的用法，不是规划。前四条是 MCP 线的，后三条是应用本身的。

**开工前的方案否决**
动大改之前，让 Codex 调 `discussion_run` 把方案丢给议事会：批判者找逻辑漏洞、风险官列最坏情况、成本专家算账。结论不满意就改方案再动手 —— 比写完再返工便宜得多。关键是**先让角色互斥**，否则只会得到一堆"这个方案很有道理"。

**红队评审（对着已定方案做对抗）**
议程只留两轮：交叉质询 + 收敛。给批判者的 `role` 写死"只负责找出这个方案会在什么情况下失败，不许肯定任何部分"。产出是一份"最可能怎么失败"的清单，而不是一份平衡的意见汇总。

**选型对比（要一个可辩护的结论）**
把两个候选方案各写一段塞进 `topic`，收敛方式选 `majorityVote`。每位成员独立投票（后投票者看不到前人的票），平票由主席裁决 —— 拿到的是一个有投票记录、可追溯的结论，而不是一段暧昧的总结。

**多轮接力，逐层收敛到能执行的粒度**
第一轮拿方向，把结论当新议题再开一轮问"那第一步具体做什么"。每轮的发言都落盘，链条完整可回溯；中途中断了用「继续讨论」接着走。

**边跑边用电脑**
静默后台运行 + 窗口可移出屏幕视野，所以一场 20 分钟的讨论不影响你同时干别的。适合把讨论当"后台顾问"用：派下去，回头取结论。

**固定巡检（配自动化）**
同一组角色、同一套议程，每天或每周对着一个长期指标跑一遍（例如"这周的依赖升级有没有引入风险""这个分支的测试覆盖有没有退步"）。因为是配置好的讨论组，直接复用，不用每次重述角色。

**方法学质询**
把实验设计 / 评估口径丢进去，让风险官和批判者专门找"这个对照够不够""这个阈值为什么是 2Å""这个指标会不会被操纵"。所有账号背后是不同会话但同一个模型，所以**它的价值是逼你把假设写清楚**，不是给你一个权威答案。

## 环境要求

- macOS 14+
- Xcode 15+ / Swift 5.9+ 工具链
- Chrome（也支持 Chrome Canary / Chromium / Edge / Brave）
- **辅助功能**权限（驱动网页 UI 所必需）

## 边界

- 所有成员背后都是同一个 ChatGPT，讨论质量完全取决于角色 prompt 的差异化程度。
- 成员数受可用 Chrome Profile 数限制，一个 Profile 只能绑定一个成员。
- 不使用 API 通道做多模型讨论，也不绕过任何验证码 / 人机验证。
